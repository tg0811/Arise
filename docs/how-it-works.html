How Arise runs on the server

A beginner's guide to the pieces behind https://89-167-82-104.sslip.io: ports, firewalls, nginx, HTTPS and certbot, Docker, and how one tap on your phone travels through all of them. Plus how the fingerprint lock keeps your data yours.

Big picture Your server is an office building

Think of the Hetzner server as a building:

  • The IP address 89.167.82.104 is its street address.
  • Ports are numbered doors. Every visitor arrives at the address and a door number.
  • The firewall is the security guard who decides which doors are open at all.
  • nginx is the receptionist behind doors 80 and 443, sending each visitor to the right office.
  • Docker is a sealed office room where one app lives with everything it needs.
  • certbot fetches the official ID card that proves the building is who it claims to be (HTTPS).

Doors Ports

One server runs many programs at once, so the port number says which program a request is for. A few numbers are conventions that every browser knows:

PortUsed forOn your server
22SSH: you logging in to the terminalopen
80Plain web, http://nginx
443Secure web, https://nginx (after certbot)
8787Arise itself. Just a number we pickedonly reachable from inside the server
5173The Vite dev server on your laptopnot used in production

When you type https://example.com, the browser silently goes to door 443. Any other door has to be written in the URL, like https://example.com:8787.

Only one program can hold a port. nginx already holds 80, so Caddy (which also wanted 80) couldn't run next to it.

Security guard Firewall

A list of which doors are open from the outside. Even if a program listens on 8787, nobody on the internet reaches it if the firewall says no. You have up to two guards, and a visitor must get past both:

  • Hetzner Cloud Firewall: set in Hetzner's web console. It stands in front of the server, before traffic even arrives.
  • ufw ("uncomplicated firewall"): runs on the server itself.

For Arise both need TCP 80 and 443 open. 8787 stays closed, because only nginx needs to reach it, from inside the server.

Receptionist nginx, a "reverse proxy"

nginx is a program sitting on doors 80 and 443. It reads which name the visitor asked for and forwards them to the right place:

That's why many websites can share doors 80 and 443: each gets its own server_name block. Arise's block lives in deploy/nginx-arise.conf. 127.0.0.1 means "this same machine", so the Arise office is never visible from outside; only the receptionist talks to it.

Not used Caddy

Another receptionist, like nginx, that also fetches HTTPS certificates on its own. It was the first plan. Since you already run nginx on door 80, and two programs can't hold the same door, we use nginx + certbot instead. The result is the same.

ID card HTTPS, certificates and certbot

HTTPS does two jobs:

  1. Encrypts the traffic, so your password and data can't be read on the way (on café Wi-Fi, for example).
  2. Proves identity, so the browser knows it's talking to the real server and not an impostor.

The proof is a certificate, a signed ID card. Let's Encrypt hands them out for free, but first it checks that you control the name, by visiting your server on port 80. That's why port 80 can't be avoided.

certbot is the tool that does this for you. It asks Let's Encrypt for the certificate, edits nginx's Arise site to add door 443 and the HTTP→HTTPS redirect, and renews it automatically before it expires (about every 90 days).

Why Arise needs HTTPS: browsers only allow installing a PWA, running its service worker, and sending push notifications on HTTPS sites. The login cookie is also marked "Secure", so it's only sent over HTTPS.

Why sslip.io: Let's Encrypt won't certify a bare IP address, only a name. sslip.io is a free service where any name like 89-167-82-104.sslip.io automatically points to the IP written inside it. No domain purchase needed. When you buy arise.<domain>.com, you just point it at the same IP and run certbot again.

Sealed room Docker

Docker packages an app with everything it needs (here: Node 26, the code, its libraries) into one box.

WordMeaningIn Arise
ImageThe packed box, like an installerbuilt from Dockerfile
ContainerA running image: the app actually goingapp
DockerfileThe recipe to build the imageSoloLeveling/Dockerfile
Compose fileHow to run it: restart on crash, which folder to keep, which portdeploy/compose.yaml
VolumeA folder that lives outside the box, so it survives rebuildsdeploy/data/ (the database)

Why bother:

  • The server doesn't need Node 26 installed, so there's no version mess.
  • Arise can't interfere with the trading bot or anything else.
  • The box that works on your laptop is the same box that runs on the server.
  • Updating means building a new box and swapping it in. The database stays, because it's in the volume.

Passing it on Port forwarding

In general: "traffic arriving at door X gets passed on to door Y somewhere else". The classic example is a home router forwarding a port to your PC so friends can join a game server. You don't need router forwarding, because a Hetzner server sits directly on the internet. Two similar things do happen in your setup:

  • Docker port mapping: 127.0.0.1:8787:8787 in compose.yaml means "connect the server's door 8787 (localhost only) to door 8787 inside the sealed container". This is the hole that lets nginx reach in.
  • nginx proxying: door 443 → 127.0.0.1:8787. A smarter kind of forwarding that also looks at the name and handles HTTPS.

All together One tap on your phone, start to finish

Updates What ./deploy.sh does

  1. Copies your code from the laptop to /opt/tghf/solo-leveling on the server (with rsync). It never copies the database or .env, so live data is safe.
  2. Tells Docker to rebuild the box from the new code and swap it in (docker compose up -d --build). Downtime is a few seconds.
  3. Checks the app answers on the server, then that it answers over HTTPS.

nginx and the certificate don't change on updates. They were set up once, following docs/DEPLOY.md.

Your key The fingerprint lock (passkeys)

Arise can lock itself after 5 minutes away and open again with your fingerprint. This section explains what actually happens when you touch the sensor, and why it's safe.

The analogy: a royal seal. Imagine a king with a unique wax seal. He keeps the seal locked in a vault, and only he can open the vault. He gives the palace guards a picture of the seal's pattern.

  • When a letter arrives, the guards compare the wax stamp to their picture. If it matches, the letter really came from the king.
  • The picture is useless for making new stamps: copying it or stealing it gets you nothing.
  • The guards never need the seal itself, so the seal never leaves the vault.

In Arise: the seal is a secret key inside your phone, the vault is your phone's security chip, opening the vault is your fingerprint, and the picture is the "public key" the server keeps.

The two keys

KeyWhere it livesWhat it can do
Private key (the seal)Inside your phone's security chip. It never leaves, not even to Google or Arise.Sign things. Only after your fingerprint, face or screen PIN unlocks it.
Public key (the picture)On the Arise server, in the passkeys table.Check signatures. It can't create one, so a stolen copy is harmless.

Together they're called a passkey. The standard behind it is WebAuthn, the same technology banks, Google and GitHub use for fingerprint login.

Your fingerprint never leaves the phone

The phone reads your fingerprint, compares it to the one you registered in the phone's own settings, and only says "yes, that's the owner" to its security chip. Arise and the server never receive your fingerprint, a picture of it, or any data about it. They only ever see a signature made by the chip.

Step 2, every time: unlocking

After 5 minutes away, opening Arise shows "UNLOCK TO ARISE" and the fingerprint prompt appears by itself:

Why a fresh random code every time? So an old signature is worthless. Even if someone recorded a past unlock, replaying it fails, because the server now asks to sign a different code. It's like a bank asking for a new OTP each time instead of accepting yesterday's.

Why the lock lives on the server

There are two ways to build an app lock:

  • A curtain (weak): the phone loads all your data, then covers it with a "Locked" picture. The data is already on the phone; someone skilled could look behind the curtain.
  • A safe (what Arise does): while locked, the server answers every request with "locked, no data" (the code is 423). The phone has nothing to show until step 5 succeeds. The app also clears what it had in memory as soon as it locks. There's nothing behind the curtain.

The 5-minute rule

  • Every time the app talks to the server, the 5-minute timer restarts. While Arise is open on screen, it checks in every 30 seconds, so it stays unlocked while you use it.
  • Close it, switch to another app, or let the screen sleep for 5 minutes, and the server marks this device as locked.
  • Each device is locked separately: unlocking your phone doesn't unlock your laptop.

Fallbacks and special cases

SituationWhat happens
Sensor fails, wet finger, you're wearing glovesTap Use password instead. Your password always works.
A device without a fingerprint set up (e.g. a laptop)It still locks after 5 minutes, and unlocks with your password. Laptops with Windows Hello or Touch ID can set up their own passkey too.
Private habits and questsThe Use fingerprint button shows them for 5 minutes, same as typing the password.
You get a new phoneLog in with the password, then set up the fingerprint again on the new phone. Remove the old phone's passkey in Settings → App lock.
Your phone is lost or stolenThe thief would need your fingerprint, face or phone PIN to use the passkey. To be safe, open Arise on another device and remove that phone's passkey in Settings, or change your password, which also signs out every other device.
Arise moves to a new domainPasskeys are tied to the site's name, so set the fingerprint up again on the new address.

A bonus: passkeys can't be phished. Each passkey belongs to one site name (89-167-82-104.sslip.io). If a fake look-alike site asked your phone for a signature, the phone would refuse, because the name doesn't match. A typed password can be tricked out of you; a passkey can't.
